# 评测设计

## 一、要回答的问题

这套系统真的比"直接问模型"更好吗？好在哪、好多少？

没有评测，这就是一句无法验证的主张。所以评测集要做的不是"证明它好"，而是**给它一个能被证伪的机会**。

## 二、三臂对照（消融实验）

关键设计：**固定模型，只改变上下文与流程**。这样分离出的是"流程的贡献"，而不是"换了个更聪明的模型"。

| 臂 | 条件 | 检验什么 |
| --- | --- | --- |
| A 裸问 | 只给情景，不给语料、不给规范 | 基线：模型凭常识作答 |
| B 有语料 | 情景 + 检索到的原文片段，不给规范 | 语料本身值多少 |
| C 完整流程 | 情景 + 语料 + 工作规范（分层、筛选、预算、来源标记、风险红线） | 规范值多少 |

三臂的提示词模板在 `prompts/`。**同一情景、同一模型、同一温度**，只换条件。

## 三、指标

### 可自动化的（`score.py` 直接算）

| 指标 | 定义 | 为什么关键 |
| --- | --- | --- |
| **引文可核性** | 输出中的每条引文能否在语料库中定位到 | 编造引文是这类系统的头号失败模式，且完全不需要主观判断 |
| 幻觉引文数 | 完全找不到出处的引文条数 | 上面那个指标的反面，单列出来更醒目 |
| 来源标记覆盖率 | 带"原文／史家评／今人解读"标记的引文占比 | 防止把后人判断当史实 |
| 结构完整度 | 是否覆盖 9 个规定字段 | 流程有没有被真正执行 |

### 需要人判或模型判的（本仓库暂不自动化）

- **结构匹配度**：检索到的案例与情景内核是否真的同构（不是主题相近）
- **可执行性**：行动方案是否落到具体动作与检验点
- **风险提醒恰当性**：有没有把历史案例当概率预测

这三项在 `rubric.md` 里给了评分细则，人工或另找模型评分均可。

## 四、已知局限（必须写明）

1. **裁判与选手同源。** 完整流程的输出由本项目的作者产出，评分脚本也是作者写的。为避免自我美化，评分脚本只采用**可机械验证**的指标（引文能否在语料中找到），不引入主观打分。
2. **上下文污染。** 作者读过全部语料，无法装作没读过。因此 A、B 两臂**必须由独立上下文生成**（另起一次对话或调用 API），不能由作者凭记忆手写。
3. **样本量小。** 目前只有 1 个情景。结论只能作为方法可行性演示，不能作为统计证据。
4. **语料不可分发。** 引用核对依赖本地语料库。外部复现时需自备同源语料，或用 `data/sample/` 验证脚本逻辑。

## 五、怎么跑

```bash
# 对一份输出打分（引用核对需要语料目录）
python eval/score.py --analysis eval/results/arm-c-full.md --corpus data/sample

# 输出 JSON，便于横向对比
python eval/score.py --analysis eval/results/arm-c-full.md --corpus <语料目录> --json eval/results/arm-c-full.json
```

## 六、目录

```
eval/
├── README.md        本文件：设计、指标、局限
├── rubric.md        人判指标评分细则
├── score.py         自动打分器（引文可核性 / 来源标记 / 结构完整度）
├── scenarios/       情景定义
├── prompts/         三臂提示词模板
└── results/         各臂输出与评分结果
```
